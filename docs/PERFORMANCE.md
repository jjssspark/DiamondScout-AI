## 모델 정확도 (2025시즌 Statcast, held-out 평가)

| 모델 | 피처 | 프로덕션 사용 여부 | 테스트 셋 | top-1 | top-3 | 모델 크기 |
|---|---|---|---|---|---|---|
| **LightGBM** | 88 | **사용 중** | 88,983건 | **43.7%** | **85.7%** | 9.89MB |
| RandomForest (보강 피처) | 88 | 미사용 (비교용) | 88,983건 | 42.2% | 83.5% | 188MB |
| RandomForest (기존) | 56 | 2026-08-17까지 사용 | 88,983건 | 39.5% | 78.7% | 188MB |
| LSTM (Keras) | 56 | 미사용 (오프라인 평가만) | 10,000건 | 40.7% | 81.6% | 0.4MB |
| GRU (numpy 서빙 경로) | 45 (lag 9필드 x 5스텝) | 미사용 (Task 7) | 88,983건 | 39.0% | 79.4% | 0.06MB |

- 출처: `output/metrics/lgbm_metrics_2025.json`, `feature_gain_2025.json`, `data/processed/model_outputs/metrics_2025.json`
- 앞의 세 줄은 **동일 split·동일 테스트 셋**이라 그대로 비교할 수 있다. LSTM만 테스트 셋 크기가 달라 엄밀한 동일 조건이 아니다.
- 개선분 분해: 피처 보강이 top-1 +2.6%p, 모델 교체가 +1.6%p. top-3는 피처 +4.8%p, 모델 +2.2%p로 피처 쪽 기여가 더 크다.

### LightGBM + GRU 앙상블 (Task 8 게이트)

`p = (1-w) * LightGBM + w * GRU`로 확률을 가중 평균했다. w는 **val에서만** 골랐고 test는
고른 뒤 한 번만 봤다. GRU 확률은 학습 경로(Keras)가 아니라 서빙 경로(numpy `SeqPredictor`)로 뽑았다.

| | LightGBM 단독 | 앙상블 (w=0.30) | 차이 |
|---|---|---|---|
| val top-1 | 44.02% | 44.18% | +0.16%p |
| test top-1 | 43.71% | **44.13%** | **+0.42%p** |
| test top-3 | 85.73% | **86.44%** | **+0.71%p** |

**게이트 판정이 갈린다.** 문구("val에서 단일 모델을 못 이기면 채택하지 않는다")는
점추정 기준으로 통과했지만, val 이득은 통계적으로 노이즈와 구분되지 않는다.

| | 한쪽만 맞힌 샘플 (LightGBM / 앙상블) | McNemar p |
|---|---|---|
| val | 3,677 / 3,819 | **0.103 — 유의하지 않음** |
| test | 3,426 / 3,794 | **1.6e-05 — 유의함** |

채택을 지지하는 근거는 val이 아니라 test와 가중치 곡선의 모양이다. w=0.05~0.35 구간
일곱 개가 **전부** 단독을 넘고(부호가 일관), top-3는 val·test 양쪽에서 함께 오른다.
단일 w가 운으로 맞은 형태가 아니다.

GRU 단독은 39.0%로 LightGBM보다 4.7%p 낮다. 그런데도 섞으면 오르는 건 **틀리는 지점이
다르기 때문**이다 — LightGBM은 gain의 81%를 prior에 쓰고, GRU는 prior를 아예 보지 않고
직전 5구의 궤적만 본다.

- 출처: `output/metrics/ensemble_gate_2025.json`, 재현: `./venv/bin/python scripts/eval_ensemble.py`
- **아직 서빙에 반영하지 않았다.** 위 43.25%/85.56% 서빙 수치는 LightGBM 단독 기준이다.

### 서빙 시점의 실제 정확도

위 43.7%는 모든 피처를 실측했을 때의 값이다. 앱은 경기 상태를 모르기 때문에(받는 것은 볼카운트와 `build_default_recent_pitches`가 합성한 최근 5구뿐) 세 피처를 관측할 수 없고, `models/serving_priors/temporal_defaults.json`의 train 대표값으로 고정한다.

| 구성 | top-1 | top-3 |
|---|---|---|
| 전 피처 실측 | 43.71% | 85.73% |
| **서빙 구성** | **43.25%** | **85.56%** |

관측 불가 세 피처(`pitcher_pitch_count_game`, `times_through_order`, `prev_pitch_outcome_enc`)의 gain 중요도 합이 0.89%라 손실이 0.46%p에 그친다. `pitch_of_atbat`은 `balls+strikes+1`로 근사하며 실제값과 84.9% 일치한다(파울이 카운트를 올리지 않아 어긋난다).

### 피처 중요도

| 그룹 | gain 비중 |
|---|---|
| prior 22개 (투수 아스널 · 카운트 조건부) | **81.45%** |
| 타자 매치업 4개 | 1.55% |
| 시간·피로 6개 | 1.30% |
| 기존 56개 | 나머지 |

prior가 모델의 대부분을 지고 있어서, 서빙 prior 테이블이 학습에 쓴 것과 다르면 정확도가 예외 없이 무너진다. 그래서 `data/build_enriched_dataset.py`가 학습 데이터와 `models/serving_priors/`를 **함께** 생성한다.

## 서비스 재랭킹의 기여도 (타자 모드)

화면에 보이는 최종 추천은 모델 출력 그대로가 아니라 `ScoutingService`가 재랭킹한 결과다. 재랭킹이 도입될 당시의 근거는 "모델 feature에 선수 ID가 없다"는 것이었는데, LightGBM 전환으로 그 전제가 사라졌다(prior가 gain의 81%). 같은 정보를 모델과 서비스가 두 번 반영하는지 측정했다.

측정: test split에서 4,000구를 무작위 추출(seed 42), 서빙 구성으로 맞춘 뒤 실제 다음 구종과 대조.

| 방식 | top-1 | top-3 |
|---|---|---|
| 모델 단독 | 0.4392 | 0.8552 |
| 모델 + 후보 제한 | 0.4412 | 0.8675 |
| 재랭킹 (현행 화면) | 0.4435 | 0.8692 |

**결론: 재랭킹은 모델을 깎지 않는다.** 다만 이득의 출처가 갈린다.

- **후보 제한**(그 투수가 실제로 던지는 구종만 후보로 둠) — top-3 이득의 88%(+0.0123)가 여기서 나온다. 모델에 없는 진짜 정보다.
- **가중 혼합**(모델 25% + 카운트 성향 50% + 구사 비율 25%) — 기여가 +0.0023/+0.0017로, n=4,000의 표준오차(약 0.008) 안이다. 유의하지 않다.

두 가지 단서를 붙여둔다.

1. 이 비교는 **재랭킹에 유리하게 기울어 있다.** 재랭킹이 쓰는 `count_pitch_profile_2025.csv`·`pitcher_pitch_profile_2025.csv`는 전 시즌 집계라 test 기간 투구를 이미 포함한다. 반면 모델 prior는 train split만 본다. 그 이점을 안고도 혼합의 기여가 측정되지 않았다.
2. **투수 모드는 측정 대상이 아니다.** "던졌을 때 유리한 공"을 고르는 추천이라 정답 라벨이 없다. 여기 수치는 타자 모드("실제로 올 구종 맞히기")에만 해당한다.

조치는 하지 않았다. 근거 없이 가중치를 바꾸면 검증되지 않은 동작 변경이 된다. 재현 스크립트는 커밋하지 않았고, 재측정이 필요하면 위 절차(4,000구 추출 → `_score_batter_expected_pitch` 호출 → 대조)를 그대로 다시 수행한다.

## 다음 구종 예측 응답 시간 (로컬 측정)

측정 방법: `PredictionService`를 직접 호출해 동일 입력으로 20회 반복 추론(`predict_top_k`, k=3), `time.perf_counter()`로 측정. 환경: 로컬 macOS.

| 항목 | RandomForest (2026-08-05) | **LightGBM (2026-08-17)** |
|---|---|---|
| 추론 1회 평균 (20회) | 23.6ms | **1.73ms** |
| 추론 1회 최소/최대 | 14.4ms / 83.4ms | 1.54ms / 4.17ms |
| 모델 로드 (앱 기동 시 1회) | 1.873s | 미계측 |

출처: `output/metrics/inference_latency.json`. 188MB 랜덤포레스트 대신 9.89MB 부스터를 타면서 **13.6배** 빨라졌고, 최대값 편차도 83.4ms → 4.17ms로 줄었다.

모델 로드는 앱 기동 시 한 번만 발생하고, 이후 요청마다는 추론(수십 ms) 비용만 든다 — 사용자 체감 지연의 대부분은 예측이 아니라 아래 Q&A의 LLM 생성 구간에서 발생한다.

## Instant Scout Q&A 응답 시간 예산 (Ollama 로컬 LLM)

`services/coach_agent.py`가 실제 생성 소요 시간을 로깅하지 않아 성공 케이스의 정확한 분포는 아직 계측하지 못했다. 대신 코드에 설계된 타임아웃 예산과, 실제 로컬 실행 로그에서 관찰된 타임아웃 발생 사례를 근거로 남긴다.

| 단계 | 타임아웃 | 실패 시 동작 |
|---|---|---|
| Ollama 가용성 확인 | 1.5초 | 규칙 기반 폴백으로 즉시 전환 |
| 답변 생성 | 25초 | 규칙 기반 폴백으로 전환 |

로컬 실행 로그(`/private/tmp/diamondscout.log`, 2026-08-05)에서 실제로 이 타임아웃이 발동한 사례:
```
[경고] Ollama 답변 생성 실패, evidence 기반 fallback으로 대체: HTTPConnectionPool(host='localhost', port=11434): Read timed out. (read timeout=25)
```
`gemma2:latest` 같은 로컬 LLM은 하드웨어에 따라 생성 시간 편차가 커서, 25초 예산을 넘기는 경우가 실제로 발생한다 — 그래서 규칙 기반 폴백이 장식이 아니라 실제로 발동하는 경로임을 이 로그가 보여준다. 설계 근거는 [ADR-0002](ADR.md#adr-0002--instant-scout-qa--faiss-rag--ollama-로컬-llm-채택) 참고.
