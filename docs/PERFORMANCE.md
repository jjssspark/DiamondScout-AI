# 성능·품질 지표

## 모델 정확도 (2025시즌 Statcast, held-out 평가)

전부 같은 test split, 같은 표본(88,983건)으로 잰 값이다. 예전 표는 RandomForest를
88,983건, LSTM을 10,000건으로 비교하고 있어서 그대로 놓고 볼 수 없었다.

| 모델 | 피처 | 프로덕션 | top-1 | top-3 | 크기 | 추론 |
|---|---|---|---|---|---|---|
| 최빈 구종 고정 (FF) | — | 베이스라인 | 32.7% | 61.1% | — | — |
| GRU (numpy) 단독 | 45 | 앙상블의 한쪽 | 39.0% | 79.4% | 61KB | — |
| RandomForest (기존) | 56 | 2026-08-17까지 사용 | 39.5% | 78.7% | 188MB | 23.6ms |
| RandomForest (+보강 피처) | 88 | 미사용 (비교용) | 42.2% | 83.5% | 188MB | — |
| LightGBM (+보강 피처) | 88 | 앙상블의 한쪽 | 43.6% | 85.7% | 9.89MB | 1.67ms |
| LightGBM + GRU 앙상블 | 88 + 45 | 사용 중 | 44.1% | 86.6% | 9.95MB | 1.77ms |

- 위 수치는 전 피처를 실측했을 때의 값이다. 앱이 실제로 내는 값은 아래 "서빙 시점의 실제 정확도" 절에 따로 있다.
- 베이스라인은 train에서 제일 많이 나온 구종(FF)을 항상 찍는 경우다. top-3는 상위 3개(FF, SI, SL)를 찍는 경우다. 모델이 이걸 못 넘으면 학습한 의미가 없다.
- LSTM(Keras)은 40.7% / 81.6%였는데 10,000건으로만 재서 이 표에 못 넣는다. 같은 자리를 GRU가 대신하고 GRU는 88,983건 전체로 쟀다.
- RandomForest 두 줄은 타자 피처 누수를 고치기 전 측정이다. 다시 재려면 188MB 모델을 두 번 학습해야 해서 그대로 뒀다. 누수 폭이 top-1 0.09%p라 순위가 바뀌지는 않는다.
- 출처: `output/metrics/lgbm_metrics_2025.json`, `ensemble_gate_2025.json`, `feature_gain_2025.json`, `data/processed/model_outputs/metrics_2025.json`
- 개선분 분해: 피처 보강 top-1 +2.6%p, 모델 교체 +1.6%p, 앙상블 +0.46%p. top-3는 피처 +4.8%p, 모델 +2.2%p, 앙상블 +0.8%p로 피처 쪽 기여가 가장 크다.

### LightGBM + GRU 앙상블 (Task 8 게이트)

`p = (1-w) * LightGBM + w * GRU`로 확률을 가중 평균했다. w는 val에서만 골랐고 test는
고른 뒤 한 번만 봤다. GRU 확률은 학습 경로(Keras)가 아니라 서빙 경로(numpy `SeqPredictor`)로 뽑았다.

| | LightGBM 단독 | 앙상블 (w=0.30) | 차이 |
|---|---|---|---|
| val top-1 | 43.95% | 44.15% | +0.20%p |
| test top-1 | 43.62% | 44.08% | +0.46%p |
| test top-3 | 85.74% | 86.55% | +0.81%p |

게이트("val에서 단일 모델을 못 이기면 채택하지 않는다")를 통과했다. 짝지은 비교로도
확인했다. 두 모델이 같은 샘플을 보므로 독립 표본 비교가 아니라 McNemar가 맞다.

| | 한쪽만 맞힌 샘플 (단독 / 앙상블) | McNemar p |
|---|---|---|
| val | 3,664 / 3,844 | 0.039 |
| test | 3,360 / 3,773 | 1.1e-06 |

가중치 곡선 모양도 근거가 된다. w=0.05~0.35 구간 일곱 개가 전부 단독을 넘고 부호가
일관되며, top-3는 val과 test 양쪽에서 같이 오른다. 한 지점이 운으로 맞은 모양이 아니다.

기록해 둘 것: 타자 피처 누수를 고치기 전에는 val McNemar가 p=0.103이라 val에서는
노이즈와 구분이 안 됐다. 누수를 걷어내니 p=0.039로 내려가 val에서도 유의해졌다.
누수가 단독 쪽 성능을 부풀리고 있었던 셈이다.

GRU 단독은 39.0%로 LightGBM보다 4.6%p 낮다. 그런데도 섞으면 오르는 건 틀리는 지점이
달라서다. LightGBM은 gain의 81%를 prior에 쓰고, GRU는 prior를 아예 안 보고 직전 5구의
궤적만 본다.

- 출처: `output/metrics/ensemble_gate_2025.json`, 재현: `./venv/bin/python scripts/eval_ensemble.py`
- 서빙에 반영했다. `services/prediction_service.py`의 `SEQ_ENSEMBLE_WEIGHT`가 w이고,
  GRU는 numpy 추론기로 돌아 TensorFlow 의존성이 늘지 않는다(가중치 61KB).

### 타자 x 구종 피처 (재봤지만 안 씀)

인계 문서에서 가장 기대했던 후보다. 지금 타자 피처는 whiff_rate 같은 값을 전 구종
평균 4개로 눌러놔서 "이 타자가 슬라이더에 약하다"는 정보가 사라진다. 그래서 구종
축을 살려서 다시 만들고 측정했다.

만든 방식:

- 전처리에 `batter_matchup_events_{year}.csv`를 추가했다. (타자, 경기, 구종) 단위
  카운트다. split이 game_pk 기준이라 이렇게 두면 train 경기만 잘라서 집계할 수 있다.
  기존 `batter_matchup_profile`은 연도 전체로 비율이 이미 계산돼 있어서 train만
  떼어낼 방법이 없다.
- 표본이 적은 칸은 그 구종의 리그 평균 쪽으로 당겼다. `(분자 + 50*리그평균) / (분모 + 50)`.
  안 그러면 2구 중 2구 헛스윙한 칸이 1.0으로 잡히고 모델이 그 잡음을 배운다.
- whiff, hard-hit, 장타 3개 지표 x 구종 11개 = 33열.

결과다. 같은 parquet에 같은 하이퍼파라미터로 컬럼만 넣고 뺐다.

이 측정은 타자 피처 누수를 고치기 전 데이터로 했다. 세 줄이 전부 같은 데이터라
차이(base 대비)는 그대로 유효하고, 기준선 절대값만 지금과 다르다(43.71% -> 43.62%).

| 구성 | 피처 수 | val top-1 | test top-1 | test top-3 | base 대비 | McNemar |
|---|---|---|---|---|---|---|
| base | 88 | 44.02% | 43.71% | 85.73% | — | — |
| whiff만 11열 | 99 | 44.00% | 43.60% | 85.68% | -0.11%p | p=0.21 |
| 전체 33열 | 121 | 43.96% | 43.50% | 85.67% | -0.21%p | p=0.023 |

읽는 법:

- 33열은 gain의 5%를 가져간다. 모델이 무시한 게 아니다. 쓰긴 쓰는데 일반화가 안 된다.
- 열이 많아서 희석된 것도 아니다. whiff만 11열로 줄여도 이득이 0이다.
- 이 지표들이 말하는 건 "타자가 그 구종을 얼마나 못 치나"다. 우리가 맞히려는 건
  "투수가 다음에 뭘 던지나"다. 둘이 생각만큼 이어지지 않는다고 본다.

파이프라인 기본값은 꺼 둔 상태다. 재현하려면 이렇게 켠다.

```bash
./venv/bin/python data/build_enriched_dataset.py --year 2025 --with-batter-pitch
./venv/bin/python scripts/eval_batter_pitch_gain.py
```

- 출처: `output/metrics/batter_pitch_gain_2025.json`

### 타자 피처를 train 경기만으로 다시 집계

`batter_whiff_avg` 같은 타자 피처 4개는 원래 `batter_matchup_profile_{year}.csv`에서
가져왔다. 그 표는 비율이 연도 전체로 이미 계산돼 있다. 어느 타자를 쓸지는 train으로
걸렀지만 비율 자체에는 val/test 경기의 반응이 들어가 있었다. 미래를 보고 만든 피처다.

오늘 만든 `batter_matchup_events_{year}.csv`가 (타자, 경기, 구종) 카운트라 여기서
train 경기만 잘라 다시 집계했다. 거는 조건은 두 개다. train 경기이면서, 학습 행에
실제로 등장한 타자여야 한다. 경기만 걸렀더니 train 경기에 나왔지만 학습 행에는 없는
타자가 남아서, 처음 보는 타자에게 쓰는 폴백 평균을 밀어버렸다.

| | 수정 전 (누수 있음) | 수정 후 | 차이 |
|---|---|---|---|
| val top-1 | 44.02% | 43.95% | -0.07%p |
| test top-1 | 43.71% | 43.62% | -0.09%p |
| test top-3 | 85.73% | 85.74% | +0.01%p |

수치가 내려가는 게 정상이다. 누수는 오프라인 점수만 올리고 실제 서비스에서는 낼 수
없는 값이다. 폭이 작은 건 이 피처들의 gain 비중이 1.54%라서다.

곁다리 효과가 하나 있었다. 앙상블의 val McNemar가 p=0.103에서 p=0.039로 내려가 val
에서도 유의해졌다. 누수가 LightGBM 단독 쪽만 부풀리고 있었다는 뜻이다.

### 피처 중요도

| 그룹 | gain 비중 |
|---|---|
| prior 22개 (투수 아스널 · 카운트 조건부) | 81.48% |
| 타자 매치업 4개 | 1.54% |
| 시간·피로 6개 | 1.32% |
| 기존 56개 | 나머지 |

prior가 모델의 대부분을 지고 있어서, 서빙 prior 테이블이 학습에 쓴 것과 다르면 정확도가 예외 없이 무너진다. 그래서 `data/build_enriched_dataset.py`가 학습 데이터와 `models/serving_priors/`를 함께 생성한다.

## 서비스 재랭킹의 기여도 (타자 모드)

화면에 보이는 최종 추천은 모델 출력 그대로가 아니라 `ScoutingService`가 재랭킹한 결과다. 재랭킹이 도입될 당시의 근거는 "모델 feature에 선수 ID가 없다"는 것이었는데, LightGBM 전환으로 그 전제가 사라졌다(prior가 gain의 81%). 같은 정보를 모델과 서비스가 두 번 반영하는지 측정했다.

측정: test split에서 4,000구를 무작위 추출(seed 42), 서빙 구성으로 맞춘 뒤 실제 다음 구종과 대조.

| 방식 | top-1 | top-3 |
|---|---|---|
| 모델 단독 | 0.4392 | 0.8552 |
| 모델 + 후보 제한 | 0.4412 | 0.8675 |
| 재랭킹 (현행 화면) | 0.4435 | 0.8692 |

결론: 재랭킹은 모델을 깎지 않는다. 다만 이득의 출처가 갈린다.

- 후보 제한(그 투수가 실제로 던지는 구종만 후보로 둠) — top-3 이득의 88%(+0.0123)가 여기서 나온다. 모델에 없는 진짜 정보다.
- 가중 혼합(모델 25% + 카운트 성향 50% + 구사 비율 25%) — 기여가 +0.0023/+0.0017로, n=4,000의 표준오차(약 0.008) 안이다. 유의하지 않다.

두 가지 단서를 붙여둔다.

1. 이 비교는 재랭킹에 유리하게 기울어 있다. 재랭킹이 쓰는 `count_pitch_profile_2025.csv`·`pitcher_pitch_profile_2025.csv`는 전 시즌 집계라 test 기간 투구를 이미 포함한다. 반면 모델 prior는 train split만 본다. 그 이점을 안고도 혼합의 기여가 측정되지 않았다.
2. 투수 모드는 측정 대상이 아니다. "던졌을 때 유리한 공"을 고르는 추천이라 정답 라벨이 없다. 여기 수치는 타자 모드("실제로 올 구종 맞히기")에만 해당한다.

조치는 하지 않았다. 근거 없이 가중치를 바꾸면 검증되지 않은 동작 변경이 된다. 재현 스크립트는 커밋하지 않았고, 재측정이 필요하면 위 절차(4,000구 추출 → `_score_batter_expected_pitch` 호출 → 대조)를 그대로 다시 수행한다.

## 배포 구성 (Render 무료 티어, 512MB)

2티어 아티팩트를 없앴다. 예전에는 원본 RandomForest가 188MB라 38MB로 축소한 배포
전용 joblib을 따로 만들고 `PITCH_MODEL_FILE` 환경변수로 갈아 끼웠다. LightGBM으로
넘어오면서 모델이 9.9MB가 돼 그럴 이유가 사라졌다.

| 아티팩트 | 크기 |
|---|---|
| `models/next_pitch_lgbm.txt` | 9.89MB |
| `models/seq_model_weights.npz` (GRU) | 61KB |
| `models/serving_priors/` (CSV 4개 + JSON 2개) | 2.2MB |
| 합계 | 약 12MB |

지운 것: `scripts/train_deploy_model.py`, `models/next_pitch_model_deploy.joblib`(38MB),
`render.yaml`의 `PITCH_MODEL_FILE`. 서빙이 이미 LightGBM이라 그 38MB는 클론만 되고
로드된 적이 없었다.

배포 의존성에서 `scikit-learn`과 `joblib`도 뺐다. RandomForest 아티팩트를 언피클할
때만 필요했는데 추론 경로에서 빠졌기 때문이다. `backend="rf"`는 로컬 비교용으로
남기고 joblib을 그 분기 안에서 지연 import 한다. `scipy`는 따로 적지 않아도 된다 -
lightgbm이 자기 의존성으로 끌고 온다.

실측이다. sklearn, joblib, tensorflow, torch, faiss, sentence_transformers를 전부
차단한 상태에서 잰 값이라 배포 환경과 같은 조건이다.

| | 값 |
|---|---|
| PredictionService 로드 | 0.80초 |
| 예측 1회 (콜드) | 5.26ms |
| PredictionService 최대 메모리 | 155MB |
| app.py 전체 로드 | 3.26초 |
| app.py 전체 최대 메모리 | 349MB |

349MB면 512MB 티어에서 160MB 정도 여유가 남는다. RAG는 배포에서 `faiss`가 없어
`rag_service=None`으로 degrade 하는 것까지 확인했다.

## Instant Scout Q&A 응답 시간 예산 (Ollama 로컬 LLM)
