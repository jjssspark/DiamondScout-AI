## 배경 / 문제

### 1. 예측 정확도

현재 프로덕션 모델(RandomForest)의 성능은 최빈값 추측 대비 개선폭이 작다.

| 기준 | top-1 | top-3 |
|---|---|---|
| 무조건 포심(FF, 최빈 클래스) | 31.5% | 60.7% |
| **현재 RandomForest (프로덕션)** | **39.5%** | **78.7%** |
| 현재 LSTM (오프라인 평가만, 미사용) | 40.7% | 81.6% |

데이터: 2025시즌 Statcast 593,797투구 / 2,380경기 / 11개 구종 클래스.

**근본 원인 — 모델에 투수 정체성 신호가 없다.** 학습에 쓰이는 56개 피처는 전부 아래 둘뿐이다.

- 상황 피처: `balls`, `strikes`, `outs_when_up`, `inning`, `on_1b/2b/3b`, `score_diff`, `stand_enc`, `p_throws_enc`
- 직전 5구 시퀀스 lag 피처: `pitch_label_id_lag1~5`, `release_speed_lag1~5`, `pfx_x/z_lag1~5`, `plate_x/z_lag1~5`, `zone_cell_lag1~5`, `balls_lag1~5`, `strikes_lag1~5`

즉 모델은 "지금 던지는 투수가 누구인지"를 모른 채 리그 평균 분포를 학습한다. 포심·슬라이더 2개만 던지는 투수와 6개 구종을 고루 섞는 투수를 같은 조건으로 예측한다.

한편 `data/processed/` 아래에는 이미 아래 프로파일이 만들어져 있으나 **모델 피처로는 하나도 들어가지 않고**, LLM 프롬프트 텍스트로만 소비되고 있다(`app.py:817`).

| 파일 | 내용 |
|---|---|
| `pitcher_pitch_profile_2025.csv` | 투수별 구종 구사 비율 (아스널) |
| `count_pitch_profile_2025.csv` | 투수 × 볼카운트별 구종 비율 |
| `batter_matchup_profile_2025.csv` | 타자 × 구종별 헛스윙률/장타율 등 |
| `zone_risk_profile_2025.csv` | 구종 × 존 셀별 위험도 |

### 2. UI

2026-08-03(다크 스타디움), 2026-08-04(라이트 브로드캐스트)에 걸쳐 두 차례 개편했다. **색·타이포 시스템은 이미 일관되게 정리돼 있다** — 크림(`#f4f2ec`) / 네이비(`#14203c`) / 레드(`#c8102e`), Teko + Share Tech Mono. 이번 문제는 색이 아니라 **정보구조와 조작 방식**이다.

로컬 실행(2026-08-15) 화면에서 확인한 문제:

- **4단계 위저드의 밀도가 극단적으로 낮다.** STEP 1(매치업)은 드롭다운 2개가 전부인데 뷰포트 하나를 통째로 차지한다. 결과를 보려면 의미 없는 "다음" 클릭을 3번 해야 한다.
- **입력이 전부 폼 컨트롤이다.** 볼/스트라이크/아웃은 슬라이더, 이닝은 숫자입력, 주자는 체크박스, 초/말은 라디오. 야구 앱인데 야구처럼 조작할 수 없다.
- **선수가 ID로 노출된다.** 타자가 `Batter ID 621566`으로 표시된다 — `batter_matchup_profile`에 이름 컬럼이 없어서다(`app.py:94`에 기존 주석 있음).
- **스트라이크존이 마지막에야 등장한다.** 이 앱의 주인공이 결과 화면 하단에 있다.
- **결과가 세로 스크롤 나열이다.** Top-3 → 추천 구종 → 피해야 할 구종 → 약점 요약 → 위험도 카드 순으로 길게 이어져 한눈에 안 들어온다.
- 화면 하단에 큰 빈 공간이 남고, `다시 분석` 버튼이 전체 폭을 차지해 위계가 어긋난다.

사용자 요구: "더 정확하게 / 반응형 + 야구 느낌 / 보기 좋고 쉽게, 직관적으로, 게임처럼 / 지금 너무 복잡함"

## 목표

1. 다음 구종 예측 top-1을 **47% 이상**, top-3를 **85% 이상**으로 올린다.
2. Render 무료 티어(512MB RAM) 데모를 계속 살린다.
3. 4단계 위저드를 **한 화면 콘솔**로 접어 결과까지의 클릭 수를 줄인다.
4. 입력을 폼이 아니라 **게임 조작**으로 바꾼다.
5. 데스크톱·태블릿·모바일 반응형을 실제로 동작시킨다.
6. 표시 확률이 실제 빈도와 맞도록 캘리브레이션한다.

## 트랙 A — 예측 정확도

### A-1. 피처 보강 (최대 레버)

`data/preprocess_statcast.py`의 데이터셋 빌드 단계에 아래 피처군을 추가한다. **모든 피처는 "해당 투구 시점 이전 데이터만" 사용해 누수를 막는다.**

**(a) 투수 아스널 prior — 11개**

투수별 구종 구사 비율을 11개 클래스 각각에 대해 컬럼으로 편다.
`pitcher_prior_FF`, `pitcher_prior_SI`, ... `pitcher_prior_OTHER`

**(b) 카운트 조건부 prior — 11개**

투수 × 현재 볼카운트(balls, strikes)에 해당하는 구종 비율.
`count_prior_FF` ... `count_prior_OTHER`

표본이 적은 카운트(예: 3-0)는 투수 전체 아스널로 shrinkage 스무딩한다:
`prior = (n_count * ratio_count + k * ratio_pitcher) / (n_count + k)`, k=20

**(c) 타자 매치업 약점 — 4개**

현재 타자가 해당 투수의 주력 구종에 보이는 반응 지표를 요약.
`batter_whiff_vs_top1`, `batter_hardhit_vs_top1`, `batter_whiff_avg`, `batter_xbh_avg`

**(d) 시간·피로 피처 — 6개 (현재 완전히 없음)**

| 피처 | 의미 |
|---|---|
| `pitch_of_atbat` | 이번 타석 내 몇 번째 투구인가 |
| `pitcher_pitch_count_game` | 오늘 경기 누적 투구수 (피로도 대리 변수) |
| `times_through_order` | 타순 순회 횟수 (1/2/3순회) |
| `same_pitch_streak` | 같은 구종을 연속 몇 개 던졌는가 |
| `prev_pitch_outcome_enc` | 직전 투구 결과 (스트라이크/볼/파울/인플레이) |
| `is_first_pitch_of_ab` | 초구 여부 |

**(e) 누수 방지 규칙**

- (a)(b)(c)의 prior는 **train split에서만 집계**해 val/test에 조인한다. 전체 데이터로 집계하면 test 정보가 train에 새어 들어간다.
- 기존 `time_based_split`(game_pk 시간순)을 그대로 쓴다.
- train에 없던 투수/타자는 리그 평균 분포로 채운다(cold start).

**검증**: 피처 추가 전후로 동일 split·동일 모델(RandomForest)을 학습해 top-1/top-3 델타를 기록한다. 이 단계만으로 top-1 +5%p 이상 오르지 않으면 조인 로직에 버그가 있다고 보고 중단·점검한다.

### A-2. LightGBM 전환

RandomForest → LightGBM(`multiclass`, 11 클래스)으로 교체한다.

**선택 이유**
- **모델 크기**: RF는 현재 188MB(축소판 40MB). LightGBM은 동급 성능에서 수 MB 수준이다. Render 512MB 제약이 오히려 풀린다.
- **정확도**: 표 형태 다중분류에서 GBDT가 RF보다 일반적으로 우세하다.
- **추론 속도**: 현재 23.6ms 대비 개선 예상 (예산 내 유지가 목표, 회귀 없으면 통과).

**하이퍼파라미터 탐색**: val split 기준으로 `num_leaves`, `learning_rate`, `min_data_in_leaf`, `feature_fraction` 4개만 좁게 탐색한다. early stopping은 val multi_logloss 기준.

**폐기 검토**: LightGBM이 val에서 보강 피처 RF를 못 이기면 RF를 유지하고 A-3으로 넘어간다. 이 판단 근거를 문서에 남긴다.

### A-3. 시퀀스 모델 앙상블

기존 `models/deep_next_pitch_model.py`(Keras)를 GRU 기반으로 정리해 학습하고, **가중치를 `.npz`로 내보내 추론은 numpy로 수행**한다.

**왜 LSTM이 아니라 GRU인가**: GRU는 게이트가 3개(LSTM은 4개)라 파라미터가 약 25% 적고 순전파 구현도 짧다. 이 규모의 시퀀스 과제에서 두 구조의 성능 차이는 통상 미미하다. 기존 LSTM 대비 성능이 떨어지면 LSTM으로 되돌린다.

**왜 numpy 내보내기인가**: TensorFlow는 설치 용량만 수백 MB라 Render 무료 티어에 올릴 수 없다. 하지만 GRU 순전파는 행렬곱과 시그모이드/탄젠트뿐이라 numpy로 30~40줄이면 구현된다. 학습은 로컬에서 Keras로, 서빙은 numpy로 분리하면 배포 의존성이 늘지 않는다.

- 입력: 직전 N=8구 시퀀스 (구종·구속·무브먼트·위치·카운트)
- 출력: 11클래스 확률
- 내보내기: `models/seq_model_weights.npz` (예상 수 MB)
- 추론 모듈: `models/seq_infer.py` — numpy만 의존

**앙상블 방식**: 가중 평균 `p = w * p_lgbm + (1-w) * p_seq`. `w`는 val split에서 top-1 기준으로 격자 탐색(0.0~1.0, 0.05 간격).

**검증**: 앙상블이 val에서 단일 LightGBM을 못 이기면 **앙상블을 채택하지 않고** LightGBM 단일로 간다. 이 결과도 문서에 남긴다 — 앙상블이 항상 이긴다는 보장은 없다.

### A-4. 확률 캘리브레이션

화면에 "포심 31.7%"를 그대로 표시하는 앱이므로 확률이 실제 빈도와 맞아야 한다.

- val split에서 multiclass isotonic 또는 temperature scaling 적용, ECE(Expected Calibration Error)로 비교해 낮은 쪽 채택
- test split에서 신뢰도 다이어그램을 `output/` 아래 저장
- **캘리브레이션은 top-k 정확도를 바꾸지 않는다** — 목적은 표시 숫자의 정직함이다

### A-5. 2-티어 모델 아티팩트

| 티어 | 파일 | 용도 | 제약 |
|---|---|---|---|
| **full** | `models/next_pitch_lgbm.txt` + `seq_model_weights.npz` | 로컬·문서 기재 성능 | 없음 |
| **deploy** | `models/next_pitch_lgbm_deploy.txt` | Render 무료 티어 | 메모리 512MB |

LightGBM 전환 후 full 모델 자체가 충분히 작으면 **두 티어를 하나로 합친다.** 그 경우 `scripts/train_deploy_model.py`는 폐기하고 문서에 사유를 남긴다. 크기 측정 후 결정한다.

### A-6. 성능 문서 갱신

`docs/PERFORMANCE.md`를 아래 형태로 재작성한다. **각 모델을 동일 test split·동일 표본 수로 재평가한다** — 현재 문서는 RF(88,983건)와 LSTM(10,000건)을 서로 다른 표본으로 비교하고 있어 엄밀하지 않다고 스스로 각주에 적어둔 상태다.

구현 방식: Gradio 기본 컴포넌트를 숨기고 `gr.HTML`로 그린 컨트롤 + 클릭 이벤트를 숨은 `gr.Number`/`gr.State`에 반영한다. 상태의 단일 진실 공급원은 Gradio 쪽 state로 유지한다.

### B-5. 결과 표현

- **Top-3**: 존 우측에 가로 게이지. 1위는 레드 강조 + 수치 모노스페이스

## UI 컨펌 게이트 (필수)

**사용자 지시**: UI는 앱에 적용하기 전에 목업을 보여주고 컨펌을 받는다.

절차:

1. `output/mockups/` 아래에 **클릭 가능한 정적 HTML 목업**을 만든다 — 실제 CSS·SVG·인터랙션(볼카운트 토글, 주자 클릭, 존 하이라이트) 포함, 데이터는 하드코딩
2. Artifact로 게시해 **링크를 사용자에게 전달**한다
3. 사용자가 데스크톱·모바일에서 직접 확인
4. **컨펌을 받기 전에는 `app.py`와 `ui/*`에 UI 변경을 적용하지 않는다**
5. 수정 요청이 오면 목업을 고쳐 다시 링크 전달. 승인될 때까지 반복
6. 승인 후에만 실제 적용 착수

트랙 A(모델)는 이 게이트와 무관하게 병행 진행한다.

## 실행 순서

| 순서 | 작업 | 검증 |
|---|---|---|
| 1 | 피처 보강 (A-1) — 누수 방지 조인 포함 | 동일 split RF 재학습, top-1 +5%p 이상 |
| 2 | UI 목업 제작 (B-1~B-5) | 사용자 컨펌 ← **게이트** |
| 3 | LightGBM 전환 + 튜닝 (A-2) | val에서 보강 RF 초과, 크기 측정 |
| 4 | GRU + numpy 내보내기 + 앙상블 (A-3) | val에서 단일 LGBM 초과 시에만 채택 |
| 5 | 캘리브레이션 (A-4) | ECE 개선, 신뢰도 다이어그램 저장 |
| 6 | 배포 아티팩트 결정 (A-5) | Render 메모리 실측 |
| 7 | `ui/` 파일 분리 (B-6) — 순수 이동 | `python app.py` 기동 + 기존 테스트 통과 |
| 8 | UI 실제 적용 (B-1~B-5) | 반응형 4폭 확인, 회귀 없음 |
| 9 | 문서 갱신 (A-6) + ADR-0003 | — |

1과 2는 병행 가능하다. 7은 8의 선행조건이다 — 모놀리스 상태로 UI를 갈아엎으면 되돌리기 어렵다.

## 리스크

| 리스크 | 대응 |
|---|---|
| prior 피처에서 데이터 누수 → 정확도가 비현실적으로 높게 나옴 | train split에서만 집계. 누수 회귀 테스트 필수. top-1이 60%를 넘으면 누수를 의심하고 검증 |
| LightGBM이 RF를 못 이김 | RF 유지하고 근거 문서화. 피처 보강 효과는 그대로 남음 |
| 앙상블 개선폭이 미미 | 채택하지 않음. 복잡도를 늘리지 않는다 |
| numpy GRU 순전파 구현 오류 | Keras 출력과 수치 비교 테스트로 방어 |
| Gradio HTML 컨트롤 ↔ state 동기화 깨짐 | state를 단일 진실 공급원으로 두고 HTML은 표시 전용. state 반영 테스트 추가 |
| UI 전면 개편 중 기능 회귀 | 파일 분리(순수 이동)를 먼저 커밋해 되돌릴 지점을 만듦 |
| 재학습 시간 (59만 행) | 로컬 학습. 소요 시간 측정해 기록 |

- GRU 시퀀스 길이 N=8은 초기값이며 val 성능으로 조정한다
