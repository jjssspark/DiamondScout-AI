## TS-010 · GRU 학습이 CPU 0%로 65분 정지

증상. `scripts/train_seq.py`가 parquet를 읽은 뒤 `model.fit()`에서 멈춘다. 예외도 로그도
없고 CPU는 0%다. 65분간 아무 변화가 없었다.

느려서가 아니었다. 같은 41만 행을 합성 numpy 배열로 넣으면 1에폭이 4.9초에 끝난다.

어떻게 좁혔나. 추측을 검증하기 전에 `faulthandler.dump_traceback_later()`로 멈춘 지점의
스택을 떴다. 설치가 필요 없고 한 줄이면 된다. 학습 연산이 아니라 변수 초기화 단계의 첫
eager 연산에서 블록돼 있었고, CPU가 0%라는 건 스핀이 아니라 락 대기라는 뜻이었다.

그다음 2×2로 격리했다.

| 조건 | 결과 |
|---|---|
| pyarrow 안 씀 | OK 1.3초 |
| `import pyarrow`만 (parquet은 안 읽음) | 교착 |
| parquet 읽음 | 교착 |
| keras를 먼저 import한 뒤 pyarrow | OK 2.3초 |

parquet를 읽는 행위가 아니라 pyarrow를 TensorFlow보다 먼저 import하는 게 조건이었다.
5천 행에서도 똑같이 멈춘다. 데이터 크기와 무관했다.

원인. 둘 다 absl 심볼을 weak definition으로 내보낸다(pyarrow 1,438개 / TF 34,862개).
macOS dyld는 weak 정의를 이미지 간에 하나로 합치고 먼저 로드된 쪽이 이긴다. `import pandas`가
pyarrow를 먼저 끌고 오면 TF가 Arrow판 absl 뮤텍스를 쓰게 되고, 첫 연산에서 깨어나지 않는
락을 기다린다. 예외가 없는 것도 CPU가 0%인 것도 전부 락 대기라서 그렇다.

해결. `import keras`를 pandas 위로 올리는 한 줄. 65분 무변화가 에폭당 12초로 바뀌었다.

덤. 같은 원인이 pytest에도 잠복해 있었다. 파일 하나씩 돌리면 106건 전부 통과하는데 붙여
돌리면 교착한다. 수집이 알파벳순이라 pandas를 쓰는 파일이 keras를 쓰는 파일보다 먼저 온다.
`tests/conftest.py`로 막았다.

배운 것. 예외 없이 CPU 0%로 멈추면 그건 락 대기다. 성능 문제로 접근하면 시간을 버린다.
그리고 격리 실험은 2×2로 짜야 원인이 갈린다. "pyarrow를 쓰면 멈춘다"까지는 알았지만
import만 하는 조건과 read까지 하는 조건을 안 나눠서 "데이터를 읽는 게 문제"라는 틀린 방향으로
갔었다.

## TS-009 · repo 루트의 `data/` 폴더 안에서 `No module named 'data'`

증상. `python data/preprocess_statcast.py --year 2025`가 즉시 죽는다. `data/` 폴더도
`data/player_names.py`도 명백히 존재하고, 같은 import를 쓰는 테스트 53개는 전부 통과한다.

원인. 파이썬은 스크립트를 직접 실행하면 `sys.path[0]`을 그 스크립트가 있는 디렉터리로 잡는다.
`python data/preprocess_statcast.py`는 `sys.path[0] = <repo>/data`가 되므로 `data`라는 이름의
패키지를 찾을 위치에 repo 루트가 없다. pytest는 rootdir를 sys.path에 넣고 `python -c`는 CWD를
넣기 때문에 둘 다 정상이었다.

즉 코드가 아니라 실행 방식에만 의존하는 문제였다.

해결. 스크립트 상단에서 repo 루트를 `sys.path`에 넣는다. 그리고 `--help`만 호출해 CLI 진입점이
뜨는지 보는 테스트를 추가했다. pytest만 돌려서는 절대 안 잡히는 종류라 별도 테스트가 필요했다.

한참 동안 아무도 눈치채지 못했다.

왜 안 보였나. 텍스트와 그림이 서로 다른 경로로 만들어졌고, 검증은 텍스트만 보고 있었다.
그림이 틀려도 문구가 맞으니 "맞게 동작한다"고 넘어갔다.

해결. 투영 결과로 좌우 반전 여부를 직접 판정하는 자체 점검을 씬 엔진에 넣었다. 통과하면 조용하고
깨지면 콘솔에 남긴다. 사람 눈으로 매번 확인하지 않아도 되게 만든 게 핵심이다.

## TS-007 · 검증 세 종류를 다 통과했는데 주기능이 죽어 있었음

증상. 렌더링 함수를 `ui/` 하위로 옮기는 "순수 이동" 리팩터링을 한 뒤, 분석 실행이 `NameError`로
전부 실패했다. 앱은 정상 기동하고 화면도 그려져서, 버튼을 누르는 순간에만 터졌다.

무엇이 통과했나. 바이트 동일성 검증, 코드 리뷰, 테스트 23개. 셋 다 통과했다.

원인. 함수를 옮기면서 `app.py`에 남은 호출부 4곳의 import를 빠뜨렸다. import 한 줄이었다.

왜 안 잡혔나. 세 검증 모두 "실제로 버튼을 눌러보는" 경로가 아니었다. 기동과 렌더링까지만 확인하면
호출 시점에 터지는 오류는 통과한다.

배운 것. "순수 이동"이라는 말이 안전을 보장하지 않는다. 옮긴 뒤에는 옮긴 함수를 실제로 부르는
경로를 한 번은 밟아봐야 한다.

## TS-006 · 배포처로 고른 Hugging Face Spaces가 402

증상. 번들 207MB를 준비하고 CLI 로그인까지 끝낸 뒤 Space를 만드는 시점에 막혔다.

```
402 Client Error: Payment Required
Static Spaces are free for everyone, but hosting Gradio and Docker Spaces on
free cpu-basic requires a PRO subscription.
```

원인. 무료 cpu-basic에서 Gradio·Docker Space 호스팅이 PRO 전용으로 바뀌어 있었다. 무료로 남은
건 Static Space뿐인데 이 앱은 서버 사이드 추론이 필수라 대체가 안 된다.

진짜 문제는 순서였다. "Gradio 앱이면 HF Spaces 무료 티어가 표준"이라는 전제로 배포처를 먼저 정하고
번들부터 만들었다. 그 시점의 무료 조건을 확인하기 전에 준비 작업을 시작한 게 손실의 원인이었다.

해결. Render 무료 티어(512MB)로 옮기고 그 한도에 맞게 줄였다. 의존성에서 tensorflow, faiss,
sentence-transformers를 빼고, 모델은 후보 4개를 실제로 학습해 재본 뒤 188MB 대신 38MB짜리를
골랐다(손실 0.55%p).

덤으로 알게 된 것. 메모리 한도라는 강제 제약이 생기면서 두 가지를 측정으로 확인했다. RAG가 답변
생성에 실제로는 안 쓰인다는 것, 모델을 4.9배 줄여도 손실이 0.55%p뿐이라는 것. 제약이 없었으면
둘 다 안 재봤을 것이다.

배운 것. 배포 작업의 순서는 번들 준비 → 배포처 선정이 아니라, 배포처의 현재 제약 확인 → 그
제약에 맞춘 번들 준비여야 한다. 플랫폼 무료 정책은 자주 바뀐다.

## TS-005 · PDF에서 라틴 악센트 문자가 통째로 빠짐

증상. 해외 선수 이름의 í, ó, ñ 같은 글자가 PDF에서 사라졌다.

첫 가설과 그게 틀린 이유. "AppleGothic이 오래된 폰트라 그렇다"고 보고 최신 한글 폰트인
Apple SD Gothic Neo로 바꿔봤다. 그런데 직접 렌더링해서 경고를 캡처해보니 두 폰트 모두 똑같이
`Glyph 225/243/244 missing`이 났다. 한글 전용 CJK 폰트는 애초에 라틴 악센트 글리프를 포함하지
않는다. 단일 폰트를 아무리 바꿔도 안 풀리는 문제였다.

해결. 폰트를 바꾸는 게 아니라 폴백 체인으로 접근을 틀었다. matplotlib 3.6+는 `font.family`에
리스트를 주면 글리프 단위로 자동 대체한다.

```python
plt.rcParams["font.family"] = ["AppleGothic", "Arial Unicode MS"]
```

배운 것. 폰트 A→B 교체로 안 풀리면 "같은 종류끼리 비교"가 아니라 "폴백 체인"으로 문제를 다시
정의해야 한다. 그걸 경고 캡처 스크립트로 확인하고 나서야 방향을 틀 수 있었다.

## TS-004 · 채팅 버블 CSS가 안 먹힘

증상. `.bubble.user-row`에 건 배경색이 화면에 아무 효과가 없었다.

원인. 셀렉터를 Gradio의 컴파일된 CSS 파일을 grep한 결과만으로 추정했는데, 실제 라이브 DOM에서
배경이 칠해지는 요소는 그 조합이 아니라 중첩된 하위 `.message.user` / `.message.bot`이었다.
정적 CSS 검색만으로는 런타임에 실제로 어떤 클래스 조합이 그려지는지 확정할 수 없다.

해결. 라이브 DOM을 순회하며 각 노드의 `className`과 `getComputedStyle().backgroundColor`를 찍어
실제로 배경이 칠해지는 노드를 특정한 뒤 셀렉터를 교체했다. 하는 김에 봇 버블이 컨테이너 전체
폭으로 늘어나 말풍선처럼 안 보이던 것도 같이 고쳤다.

배운 것. 컴파일된 프론트엔드를 CSS로 커스터마이징할 때, 소스 파일을 검색해 얻은 클래스 이름은
"그 프레임워크가 쓰는 후보"일 뿐이다. 확신이 안 서면 라이브 DOM 검사가 항상 더 빠르고 정확하다.

## TS-003 · 새로고침 후 첫 방문에서만 버튼이 사라짐

증상. STEP4에 도달하면 "분석 실행" 버튼이 안 보이고 "다시 분석"만 보였다. 새로고침 후 첫 진입
시 100% 재현되고, 같은 세션에서 두 번째 이후 재방문하면 항상 정상이었다.

한 번 오판했다. 처음엔 브라우저 자동화에서 난 실패를 "stale element reference" 탓으로 결론짓고
완료로 보고했다. 사용자가 실사용에서 같은 증상을 다시 보고해서 재조사했다.

어떻게 확정했나. 매번 새 페이지 로드부터 시작해 클릭하고 `getComputedStyle().display`를 재는
결정론적 스크립트를 만들었다. 지연 시간을 700ms, 2s 등으로 바꿔가며 반복해 레이스 컨디션 가설을
배제했고, "새로고침 후 첫 전환은 항상 실패, 두 번째부터는 항상 성공"이라는 패턴을 확정했다.

원인. 컴포넌트가 Python 쪽 정적 초기값에서 한 번도 실제 이벤트를 거치지 않은 상태로 있다가, 그
값이 처음 바뀌는 첫 live 전환에서만 렌더링이 누락된다. 프레임워크 내부의 정확한 메커니즘까지는
파고들지 않았으므로 확인된 건 재현 패턴이고 내부 동작은 추정으로 남긴다.

해결. 두 부분으로 나눴다.

하나. 초기값을 `visible=False` 대신 `visible=True`로 선언하고, `demo.load()`에서 실제 이벤트로
한 번 `False`로 되돌린다. 그러면 사용자가 마주치는 전환은 항상 "두 번째"가 되어 안정적이다.
이미 숨겨진 조상 안에 있어서 깜빡임도 없다.

둘. "다음" 버튼은 Python 토글을 아예 없애고 CSS 형제 선택자로 숨겼다. 한 이벤트에서 두 컴포넌트를
동시에 토글하는 상황 자체를 제거했다.

배운 것. 자동화 테스트의 실패를 "도구 아티팩트"로 성급히 결론짓지 않는다. 사용자가 실사용에서
같은 증상을 다시 보고하면 그 가설은 즉시 폐기하고 처음부터 다시 봐야 한다. 겉보기엔 간헐적이던
버그를 명확한 패턴으로 바꿔준 건 결정론적 재현 스크립트였다.

## TS-002 · `position:relative` 한 줄이 베이스 3개를 한 점에 뭉치게 함

증상. 다이아몬드 중앙에 마운드 장식을 추가하자 베이스 마커 3개가 화면 위쪽 한 지점에 겹쳤다.
각각 `top: 12.1% / 50% / 87.9%`로 다른 값을 줬는데도 완전히 같은 자리에 있었다.

원인. 절대배치 요소의 `top/left` 퍼센트는 가장 가까운 positioned 조상을 기준으로 계산된다.
마운드를 그리려고 중간 wrapper에 `position: relative`를 추가하면서, 베이스 마커들의 기준 조상이
320px짜리 컨테이너에서 그 wrapper로 바뀌었다. wrapper는 높이가 거의 0이라 퍼센트 값이 사실상
0에 수렴했다.

어떻게 찾았나. `getBoundingClientRect()`로 실측하니 세 마커의 top이 245.44px로 정확히 같고
컨테이너의 실제 top과도 안 맞았다. 그 하나로 "기준 조상이 바뀌었다"는 가설이 바로 섰다.

해결. 추가했던 `position: relative` 한 줄만 제거. wrapper가 static으로 돌아가면 마운드의
절대배치는 자동으로 다음 positioned 조상을 기준으로 잡히므로 마운드 위치는 그대로 유지된다.

배운 것. 같은 컨테이너를 공유하는 다른 절대배치 요소가 있다면, `position` 값을 바꾸는 CSS 한 줄이
그 요소들의 기준 좌표계 전체를 바꿀 수 있다.

## TS-001 · 절대배치 자식만 있는 wrapper의 높이 붕괴

증상. 다이아몬드 모양으로 배치한 베이스 아이콘 세 개가 전부 아래쪽이 잘려 오각형처럼 보였다.

원인. Gradio가 체크박스 그룹을 감싸려고 자동 생성하는 `.form` div가 중간에 끼어 있는데, 그 자식이
전부 `position:absolute`라 일반 흐름 높이에 기여하지 않는다. 그래서 `.form`의 auto-height가
2px로 붕괴했고, 기본 `overflow: auto hidden` 때문에 그걸 넘는 내용이 전부 잘렸다.

헛다리. 처음엔 내가 만든 두 컨테이너에 `overflow: visible`을 걸었는데 여전히 잘렸다. 실제 클리핑
지점이 내가 만들지 않은 중간 wrapper였기 때문이다. DOM 체인을 끝까지 훑고 나서야 찾았다.

해결. 그 wrapper에 `overflow: visible`과 `height: auto`를 건다.

배운 것. 증상(베이스가 잘림)과 원인(안 보이는 중간 wrapper의 높이 붕괴)이 전혀 직관적으로
이어지지 않았다. 최종적으로 스타일링한 요소가 아니라 "내가 만들지 않은 중간 wrapper"를 의심하고
DOM 체인 전체를 훑는 게 핵심이었다.

## 되돌아보면

10건 중 6건이 "증상이 가리키는 곳과 실제 원인이 다른" 경우였다. 공통적으로 도움이 된 건 추측을
쌓기 전에 실측 도구를 먼저 쓴 것이다. `getBoundingClientRect()`, `getComputedStyle()`,
`faulthandler` 스택 덤프, 경고 캡처 스크립트 같은 것들이다.

가장 비싸게 배운 건 TS-003과 TS-007이다. 둘 다 "검증을 통과했으니 됐다"고 넘어갔다가 사용자가
다시 보고해서 돌아온 경우다. 통과한 검증이 실제 사용 경로를 밟고 있는지를 따로 확인해야 한다는
걸 두 번에 걸쳐 배웠다.
