# 프로젝트 회고

2026년 7월 2일 ~ 8월 18일. 1인 개발.

## 무엇을 만들었나

Statcast 데이터 기반 야구 스카우팅 분석 도구. 투수/타자 모드로 나눠 매치업과 경기 상황을 입력받고, 다음 구종(11개 클래스) 예측·3D 스트라이크존 시각화·PDF 리포트·Instant Scout Q&A까지 제공한다. Gradio 6.x `Blocks` 기반 단일 앱(`app.py`)이다.

배포는 Render 무료 티어(512MB)에 올라가 있다. https://diamondscout-ai.onrender.com

## 어떻게 만들었나

- 예측 모델: RandomForest baseline으로 시작해 LightGBM + GRU 앙상블로 전환했다. 피처를 보강하고(투수 아스널·카운트 조건부 prior 등 88개) LightGBM으로 바꾼 뒤 GRU 시퀀스 모델을 섞었다. GRU는 학습만 Keras로 하고 가중치를 npz로 내보내 numpy 순전파로 서빙한다. 그래서 배포에 TensorFlow가 들어가지 않는다.
- Q&A: `CoachAgent`가 방금 나온 분석 결과(예측 확률·구사 비율·상대 타자 약점·위험도)를 근거로 프롬프트를 만들고 LLM이 답한다. 가용성 확인 1.5초, 생성 25초 타임아웃, 규칙 기반 폴백까지 3중으로 막아 LLM이 죽어도 앱은 안 죽는다.
- 벡터 검색: FAISS 인덱스가 있고 질문마다 검색도 돌지만, 그 결과는 Q&A 로그에만 적재되고 답변 생성에는 들어가지 않는다. 경위는 [ADR-0008](ADR.md)에 있다.
- UI: 수업 커리큘럼이 Gradio를 전제조건으로 요구해서 별도 프론트엔드 없이 Python 한 파일에서 통합했다.

## 결과가 어떻게 나왔나

모든 모델을 같은 test split, 같은 표본(88,983건)으로 다시 비교했다.

| 모델 | 프로덕션 | 크기 | top-1 | top-3 | 추론 |
|---|---|---|---|---|---|
| 최빈 구종 고정 (FF) | 베이스라인 | — | 32.7% | 61.1% | — |
| RandomForest | 8/17까지 사용 | 188MB | 39.5% | 78.7% | 23.6ms |
| LightGBM 단독 | 앙상블의 한쪽 | 9.89MB | 43.6% | 85.7% | 1.67ms |
| LightGBM + GRU 앙상블 | 사용 중 | 9.95MB | 44.1% | 86.6% | 1.77ms |

서빙 실측 기준으로는 top-1 39.5% → 43.84%, top-3 78.7% → 86.38%다. 기획 단계 목표였던 top-3 80%는 넘겼고, top-1 47%에는 3.2%p 못 미쳤다.

개선분은 단계별로 나눠 쟀다. 피처 보강 +2.6%p, 모델 교체 +1.6%p, 앙상블 +0.46%p. 모델을 바꾼 것보다 피처를 설계한 쪽 기여가 컸다.

확률 캘리브레이션도 했다. 화면에 "포심 38.6%"를 그대로 띄우니 그 숫자가 실제 빈도와 맞아야 한다. 온도 스케일링으로 ECE 0.0126 → 0.0081. 순위를 안 바꾸는 방식이라 top-k는 그대로다.

측정 근거와 재현 명령은 전부 [PERFORMANCE.md](PERFORMANCE.md)에 있다.

## 왜 이런 선택을 했나

- 처음에 RandomForest만 프로덕션에 둔 이유: LSTM이 지표상 앞섰지만 테스트 셋 크기가 88,983건 대 10,000건으로 달라 같은 조건 비교가 아니었다. 그 차이가 진짜인지 확신할 수 없는 상태에서 TensorFlow 의존성을 들이는 건 이르다고 봤다.
- 나중에 갈아탄 이유: 같은 조건으로 다시 재니 결론이 바뀌었다. LightGBM이 정확도도 높고 크기도 19배 작았다.
- Gradio와 FAISS·Ollama: 순수 엔지니어링 최적화가 아니라 수업 커리큘럼이 요구한 스택이었다는 게 [PRD.md](PRD.md)에 명시돼 있다.
- 판단 근거는 전부 [ADR.md](ADR.md)에 Context → Decision → Consequences 형식으로 남겼다.

## 겪은 문제와 배운 점

기록은 [TROUBLESHOOTING.md](../TROUBLESHOOTING.md)에 11건 있다. 그중 배운 게 컸던 것들이다.

- GRU 학습이 예외 없이 CPU 0%로 65분간 멈췄다(TS-010). 성능 문제로 접근해서 시간을 버렸다. 스택을 떠보니 락 대기였고, 원인은 pyarrow가 TensorFlow보다 먼저 로드되면서 absl 심볼이 충돌한 것이었다. import 순서 한 줄로 해결했다. 예외 없이 CPU 0%면 그건 락 대기다.
- 리팩터링 후 주기능이 6시간 동안 죽어 있었다(TS-007). 바이트 동일성 검증·코드 리뷰·테스트 23개를 전부 통과한 상태였다. 이동 리팩터링의 위험은 옮긴 쪽이 아니라 남은 쪽에 있는데, 셋 다 그걸 안 봤다.
- 그 뒤 "잔존 참조 grep"을 완료 조건에 넣었는데, 비슷한 사고가 또 났을 때 그 처방이 무력했다(TS-009). import 문은 멀쩡하고 실행 경로가 끊긴 종류였다. 처방을 늘리는 것보다 처방이 어디까지 닿는지 아는 게 먼저다.
- 스트라이크존이 처음부터 좌우로 뒤집혀 있었다(TS-008). 숫자도 정상이고 에러도 없어서 독립 구현 두 개를 나란히 놓기 전까지 몰랐다. 코드에는 `plate_x` 음수가 어느 쪽인지가 없어서, 사구 349건을 뽑아 확인했다(좌타 음수 비율 0%, 우타 100%). 파생값의 물리적 의미는 파생식이 아니라 원본 데이터로 확인해야 한다.

## 이번 프로젝트 안에서 고친 것

8월 초 회고에 적어둔 문제들을 그대로 두지 않고 같은 프로젝트 안에서 처리했다.

| 항목 | 7월 말 | 8월 18일 |
|---|---|---|
| 테스트 | 23개 (화면 경로 0개) | 121개 |
| 모델 비교 기준 | 88,983건 vs 10,000건 제각각 | 전부 같은 split |
| 배포 | `share=True`, 1주일 후 만료 | Render 상시 |
| 기록 | 산발적 | ADR 8건, 트러블슈팅 11건 |

사고가 날 때마다 탐지 장치를 하나씩 만들었다. import 순서를 AST로 검사하는 테스트(`test_import_order.py`), CLI 진입점을 실제로 실행해보는 테스트(`test_cli_entrypoints.py`), 라이브러리 로드 순서를 고정하는 `conftest.py`. 셋 다 각각 한 번씩 사고를 겪고 나서 만들었다.

## 알면서도 남겨둔 것

- top-1 목표 47%에 3.2%p 못 미친다. 남은 후보가 하이퍼파라미터 정도인데 그것으로 3%p가 나오는 경우는 드물다. 47%가 이 피처 세트로 닿을 수 있는 수치인지부터 다시 봐야 한다.
- `app.py` 이벤트 핸들러를 지나는 스모크 테스트가 없다. TS-007을 겪고도 안 만들었다.
- `DBService`에 재연결 로직이 없다. 시작 시 1회만 확인하고, 이후 DB가 살아나도 그 세션 동안은 비활성이다([ADR-0004](ADR.md)).
- 투수 모드 추천은 정답 라벨이 없어 오프라인 검증이 원리적으로 불가능하다. 타자 모드만 쟀다.
- `ui/zone_heatmap.py`의 미사용 렌더러 5개가 좌우 뒤집힌 채로 남아 있다. 되살리려면 `cell_xy()`부터 고쳐야 한다.

## 혼자 만들면서 배운 것

리뷰해줄 사람이 없으니 내가 만든 걸 내가 검증해야 했는데 그게 잘 안 됐다.

버튼이 사라지는 버그(TS-003)를 브라우저 자동화 도구 문제로 판단하고 해결됨으로 넘겼다가, 실사용에서 같은 증상이 다시 나와 재조사했다. 도구가 실패했을 때 도구 탓으로 결론 내리기가 너무 쉬웠다. 결정론적 재현 스크립트를 만들고 나서야 패턴이 잡혔다.

반대로 코드만 봐서는 답이 안 나오는 것도 있었다. 스트라이크존 좌우 문제는 두 가설이 대등해서 아무리 봐도 안 갈렸고, 도메인 사실 한 줄을 사람에게 물은 것과 데이터를 직접 뽑아본 것이 가장 빠른 진전이었다.

판단이 막히면 지금 무엇을 근거로 그렇게 생각하는지 먼저 적어보고, 근거가 코드 안에 없으면 데이터를 보거나 물어본다. 이 습관이 남았다.
