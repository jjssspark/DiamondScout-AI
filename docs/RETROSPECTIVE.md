# 프로젝트 회고

## 무엇을 만들었나

Statcast 데이터 기반 야구 스카우팅 분석 도구. 투수/타자 모드로 나눠 STEP1~4 마법사 UI를 통해 매치업을 입력받고, 다음 구종(11개 클래스) 예측·스트라이크존 시각화·PDF 리포트·Instant Scout Q&A 채팅까지 제공한다. Gradio 6.x `Blocks` 기반 단일 앱(`app.py`)으로 구현했다.

## 어떻게 만들었나

- **예측 모델**: RandomForest baseline을 먼저 만들어 프로덕션에 붙였고, 이후 LSTM+Dense 딥러닝 모델을 추가로 학습·평가했다. 다만 LSTM은 TensorFlow 의존성이 무거워 오프라인 평가만 하고 실제 서비스 추론 경로(`PredictionService`)에는 연결하지 않았다 — `load_deep_model=True`로 호출하는 곳이 코드 전체에 없다.
- **Q&A**: 분석 결과를 FAISS에 인덱싱해 RAG로 컨텍스트를 검색하고, 로컬 Ollama(`gemma2:latest`)로 답변을 생성한다. 가용성 체크(1.5초)·생성 타임아웃(25초)·규칙 기반 폴백까지 3중으로 방어해, LLM이 죽어도 앱 자체는 안 죽게 설계했다.
- **UI**: 수업 커리큘럼이 Gradio를 전제조건으로 요구해서, 별도 프론트엔드 없이 Python 한 파일에서 백엔드·프론트를 통합했다.

## 왜 이런 선택을 했나

- RandomForest만 프로덕션에 남긴 이유: 정확도 1~3%p 차이보다 배포 단순성(TensorFlow 없이 scikit-learn만으로 기동)이 1인 개발 규모에서 더 이득이라고 판단.
- RAG+Ollama, Gradio 채택 이유: 둘 다 순수 엔지니어링 최적화가 아니라 **수업 커리큘럼이 요구한 스택**이었다는 게 `docs/PRD.md`에 명시돼 있다.
- 이 판단 근거는 전부 [`docs/ADR.md`](ADR.md)에 Context→Decision→Consequences 형식으로 남겨뒀다.

## 결과가 어떻게 나왔나

| 모델 | 테스트 셋 | top-1 | top-3 |
|---|---|---|---|
| RandomForest (실서비스 사용) | 88,983건 | 39.5% | 78.7% |
| LSTM (평가만, 미배포) | 10,000건 | 40.7% | 81.6% |

LSTM 수치가 더 높지만 테스트 셋 크기가 달라 엄밀한 동일 조건 비교는 아니다 — 포트폴리오에 성과로 쓸 때 이 단서를 반드시 붙여야 한다.

## 겪은 문제와 배운 점

- **Gradio `visible=` 첫 전환 버그**: 컴포넌트가 정적 초기값에서 벗어나는 첫 번째 `visible=` 전환이 새로고침 직후 렌더링을 누락하는 프레임워크 버그성 동작을 겪었다. `demo.load()`로 그 첫 전환을 미리 한 번 "태워버리는" 프라이밍 패턴으로 우회했다([TROUBLESHOOTING TS-003](../TROUBLESHOOTING.md)).
- **CSS 셀렉터 오판**: 채팅 버블 배경색을 처음엔 `.bubble.user-row`에 걸었다가 안 먹혀서, 브라우저 DOM을 직접 뜯어본 뒤 실제로는 `.message.user`/`.message.bot`에 배경이 걸린다는 걸 확인하고 재수정했다(TS-004). 정적 CSS 파일 grep만으로는 실제 렌더링된 DOM 구조를 확신할 수 없다는 걸 재확인.
- **폰트 글리프 누락**: PDF 리포트에서 해외 선수 이름의 라틴 악센트 문자(í/ó/ñ)가 통째로 빠지는 문제를, 폰트를 바꿔도 안 풀리는 걸 직접 검증하고 matplotlib 폰트 폴백 리스트로 근본 해결했다(TS-005).
- **문서-현실 불일치**: `CLAUDE.md`에 "git 미연동"이라고 적혀 있었지만 실제론 GitHub에 연동돼 있고 22개 커밋이 push 안 된 채 쌓여 있었다. 문서는 코드가 바뀌면 같이 안 바뀐다는 걸 보여준 사례.
- **관리 체계 정비**: 트러블슈팅 기록을 프로젝트 로컬 파일로, 아키텍처 결정을 ADR 단일 문서로 각각 분리해 축적하는 구조를 확립했다.

## 다시 만든다면 무엇을 다르게 할 것인가

- LSTM과 RandomForest를 처음부터 **동일한 테스트 셋**으로 평가했을 것 — 지금은 88,983건 vs 10,000건으로 갈려 있어 성과 지표를 그대로 인용하기 조심스럽다.
- 핵심 서비스 함수(`PredictionService` 등)에 대한 최소 테스트를 마이그레이션 3단계(`tests/` 신설)보다 미루지 않고 초기부터 같이 갔을 것.

## 알면서도 남겨둔 기술 부채

- `tests/` 디렉터리 부재 — 프로젝트 `CLAUDE.md`에도 이미 "신규 필요"로 명시돼 있음.
- `DBService` 재연결 로직 없음 — 시작 시 1회만 연결 확인하고, 이후 DB가 살아나도 세션 내내 비활성 상태로 남는다([ADR-0004](ADR.md#adr-0004--db-로깅-실패-시-핵심-기능-무중단-설계)).
- `share=True` 임시 배포 — 최대 1주일 후 링크가 만료되는 구조를 그대로 두고 있음([ADR-0005](ADR.md#adr-0005--gradio-sharetrue-임시-터널로-배포)).

## 가장 오래 붙잡은 문제

STEP4 "분석 실행" 버튼이 새로고침 직후에만 사라지는 버그(TS-003)였다. 처음엔 브라우저 자동화 도구 자체의 아티팩트로 오판하고 "해결됨"으로 보고했다가, 사용자가 실사용에서 같은 증상을 다시 보고해 재조사했다. 결정론적 재현 스크립트(새 페이지 로드마다 텍스트 매칭 클릭 + `getComputedStyle()` 검증)를 만들고 나서야 "새로고침 후 첫 번째 `visible=` 전환만 항상 실패한다"는 패턴을 확정할 수 있었다. 자동화 테스트의 실패를 도구 탓으로 성급히 결론짓지 않아야 한다는 걸 여기서 배웠다.
